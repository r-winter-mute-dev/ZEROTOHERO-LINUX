## Schlüssel, Antrag, Zertifikat

<Karte nr={1} titel="Die drei Dateien">
Für HTTPS braucht der Server zwei Dinge:

- einen **privaten Schlüssel** (`www.key`), der den Rechner nie verlässt und nur für root lesbar ist,
- ein **Zertifikat** (`www.crt`): öffentlicher Schlüssel plus Name, Gültigkeit und die Unterschrift einer **Zertifizierungsstelle** (CA).

Dazwischen steht der **Antrag** (`www.csr`, certificate signing request): öffentlicher Schlüssel und gewünschter Name, unterschrieben mit dem privaten Schlüssel. Ihn bekommt die CA, nie den Schlüssel.

```
openssl genrsa -out /etc/ssl/private/www.key 2048
openssl req -new -key /etc/ssl/private/www.key -out www.csr \
    -subj "/C=DE/O=Werkstatt/CN=www.lab.example.org" \
    -addext "subjectAltName=DNS:www.lab.example.org,DNS:lab.example.org"
```

Der Name im **Subject** ist eine Folge von Feldern: C (Land), ST, L (Ort), O (Organisation), OU, **CN** (common name). Browser schauen heute nur noch in die Erweiterung **subjectAltName** (SAN). Ein Zertifikat ohne SAN lehnen sie ab, auch wenn der CN stimmt. Ohne `-subj` fragt `openssl req` jedes Feld einzeln ab.

Alle drei Dateien sind **PEM**: Base64 zwischen `-----BEGIN …-----` und `-----END …-----`. Lesbar macht sie `openssl x509 -in www.crt -noout -text` (bzw. `req -in … -text`).
</Karte>

## Eine eigene CA

<Karte nr={2} titel="Selbst unterschreiben">
Eine **selbst signierte** Datei hat sich selbst unterschrieben, Aussteller und Inhaber sind gleich. Das ist genau, was eine CA ist: `openssl req -x509` macht aus dem Antrag sofort ein selbst signiertes Zertifikat, und OpenSSL 3 trägt dabei `CA:TRUE` ein.

```
cd /etc/ssl/werkstatt
openssl req -x509 -newkey rsa:4096 -noenc -keyout ca.key -out ca.crt \
    -days 3650 -subj "/C=DE/O=Werkstatt/CN=Werkstatt Labor CA"
openssl x509 -req -in www.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
    -copy_extensions copy -days 365 -out /etc/ssl/certs/www.lab.example.org.crt
```

`-noenc` (früher `-nodes`) lässt den Schlüssel unverschlüsselt, sonst fragt Apache bei jedem Start nach der Passphrase. `-CAcreateserial` legt `ca.srl` mit der laufenden Seriennummer an, `-copy_extensions copy` übernimmt den SAN aus dem Antrag. Das Perl-Skript **CA.pl** (`/usr/lib/ssl/misc/CA.pl -newca`, `-newreq`, `-sign`) erledigt dieselben Schritte mit `openssl ca` und einer festen Ordnerstruktur.

Wem vertraut ein Client? Den Wurzeln in seinem Speicher: auf Debian `/etc/ssl/certs/ca-certificates.crt`, gepflegt mit **update-ca-certificates** aus `/usr/local/share/ca-certificates/*.crt`; auf Red Hat `/etc/pki/tls/certs/ca-bundle.crt`, gepflegt mit **update-ca-trust** aus `/etc/pki/ca-trust/source/anchors/`. Browser haben oft einen eigenen Speicher.
</Karte>

## HTTPS in Apache

<Karte nr={3} titel="mod_ssl">
```
<VirtualHost *:443>
    ServerName www.lab.example.org
    DocumentRoot /var/www/www
    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/www.lab.example.org.crt
    SSLCertificateKeyFile /etc/ssl/private/www.lab.example.org.key
</VirtualHost>
```

Auf Debian: `a2enmod ssl` (zieht socache_shmcb nach, `ports.conf` öffnet dann `Listen 443`), Datei in sites-available, `a2ensite`, Neustart. Eine Vorlage ist `default-ssl.conf` mit dem Schnellschuss-Zertifikat `ssl-cert-snakeoil.pem` aus dem Paket ssl-cert. Auf Red Hat bringt `dnf install mod_ssl` die Datei `conf.d/ssl.conf` mit einem `<VirtualHost _default_:443>` und erzeugt beim ersten Start `/etc/pki/tls/certs/localhost.crt`.

configtest prüft, ob die Dateien existieren. Ob Schlüssel und Zertifikat zusammenpassen, merkt Apache erst beim Start (`AH02565: Certificate and private key … do not match`). Vorher prüfen kannst du es selbst: `openssl x509 -noout -modulus -in www.crt | sha256sum` und `openssl rsa -noout -modulus -in www.key | sha256sum` müssen dasselbe ergeben.

Eine HTTP-Anfrage an Port 443 beantwortet Apache mit 400 („You're speaking plain HTTP to an SSL-enabled server port“). Und curl bricht ohne Vertrauen in die CA mit Code 60 ab.
</Karte>

<Merke>genrsa → req -new (mit SAN) → x509 -req -CA. Schlüssel nach /etc/ssl/private, nur root. SSLEngine on, SSLCertificateFile, SSLCertificateKeyFile. Vertrauen: update-ca-certificates (Debian), update-ca-trust (Red Hat).</Merke>

<Hinweis titel="Prüfungstipp">
208.2 nennt /etc/ssl/ und /etc/pki/, openssl und CA.pl, SSLEngine, SSLCertificateKeyFile, SSLCertificateFile, SSLCACertificateFile und SSLCACertificatePath. Gefragt wird, welche Datei an die CA geht, welche Direktive auf Schlüssel oder Zertifikat zeigt und wie man ein selbst signiertes Zertifikat erzeugt. SSLCACertificateFile und SSLCACertificatePath nennen die CAs, deren **Client**-Zertifikate Apache bei SSLVerifyClient annimmt, sie haben mit dem eigenen Serverzertifikat nichts zu tun.
</Hinweis>
