www läuft mit HTTPS und eurer eigenen CA. Für die Kunden reicht das nicht, ihre Browser kennen die Werkstatt-CA nicht. Max hat bei der (erfundenen) CA Open Trust Lab ein Zertifikat gekauft, die Dateien liegen in ~/zert. intern soll weiter das eigene Zertifikat nutzen, auf derselben Adresse. Und der Prüfer der Firma will, dass der Server nichts Überflüssiges verrät. **Deine Mission: Bau das gekaufte Zertifikat samt Kette ein, gib intern per SNI ein eigenes Zertifikat, schalte alte Protokolle ab und härte die Antworten.** Lernziel 208.2.

## Ketten

<Karte nr={1} titel="Zwischenzertifikate">
Öffentliche CAs unterschreiben Serverzertifikate nicht mit ihrer **Wurzel**, sondern mit einem **Zwischenzertifikat** (intermediate). Die Wurzel kennt jeder Client, das Zwischenzertifikat nicht. Der Server muss es darum mitschicken:

```
Open Trust Root X1      ← im Vertrauensspeicher des Clients
  └─ OTL R3             ← schickt der Server mit
       └─ www.lab.example.org
```

Seit Apache 2.4.8 steht die Kette in **SSLCertificateFile**: zuerst das Serverzertifikat, dahinter die Zwischenzertifikate (`cat www.crt otl-r3.crt > www-kette.crt`). Das alte **SSLCertificateChainFile** geht noch, gilt aber als veraltet. Fehlt das Zwischenzertifikat, melden curl und manche Browser „unable to get local issuer certificate“, andere Browser holen es heimlich nach. Darum fällt der Fehler oft erst bei einem Kunden auf.

Was der Server wirklich schickt, zeigt `openssl s_client -connect www.lab.example.org:443 -servername www.lab.example.org -showcerts`. Unter „Certificate chain“ steht jedes Zertifikat mit Inhaber (`s:`) und Aussteller (`i:`).
</Karte>

## Mehrere Namen auf Port 443

<Karte nr={2} titel="SNI">
Bei HTTP entscheidet der Kopf `Host`, welcher virtuelle Host antwortet. Bei HTTPS muss der Server sein Zertifikat aber schon vorzeigen, bevor der Kopf kommt. Früher hieß das: eine Adresse pro HTTPS-Seite. Mit **SNI** (Server Name Indication) schickt der Client den Namen schon im TLS-Handshake mit, und Apache wählt danach den `<VirtualHost *:443>` und sein Zertifikat aus.

```
<VirtualHost *:443>
    ServerName intern.lab.example.org
    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/intern.lab.example.org.crt
    SSLCertificateKeyFile /etc/ssl/private/intern.lab.example.org.key
    …
</VirtualHost>
```

Alle heutigen Clients beherrschen SNI. Wer keinen Namen schickt (sehr alte Clients, Abrufe per IP-Adresse), bekommt den **ersten** Host für *:443 und damit dessen Zertifikat. Eine Alternative für wenige Namen ist ein Zertifikat mit mehreren SAN-Einträgen oder ein Platzhalter `*.lab.example.org`.
</Karte>

## Härten

<Karte nr={3} titel="Alte Protokolle und geschwätzige Antworten">
SSLv2 und SSLv3 sind gebrochen, TLS 1.0 und 1.1 gelten als unsicher. `SSLProtocol -all +TLSv1.2 +TLSv1.3` (oder `all -SSLv3 -TLSv1 -TLSv1.1`) lässt nur die beiden aktuellen zu. Debian 12 und Red Hat 9 sperren alles unter TLS 1.2 schon in OpenSSL selbst, die Zeile macht die Absicht aber sichtbar und übersteht Updates. `SSLCipherSuite HIGH:!aNULL:!MD5` streicht schwache Verfahren, `SSLHonorCipherOrder on` lässt den Server die Reihenfolge bestimmen. Auf Red Hat steuern die systemweiten crypto-policies (`SSLCipherSuite PROFILE=SYSTEM`), umschalten mit `update-crypto-policies --set DEFAULT|FUTURE`.

Weniger verraten, in Debians `conf-available/security.conf`:

- `ServerTokens Prod` – der Kopf lautet nur `Server: Apache` statt `Apache/2.4.71 (Debian) OpenSSL/3.0.22`.
- `ServerSignature Off` – keine Versionszeile unter Fehlerseiten und Verzeichnislisten.
- `TraceEnable Off` – die Methode TRACE spiegelt Anfragen samt Cookies zurück und wird mit 405 abgelehnt.

Zum Schluss wird HTTP nur noch zum Umleiten benutzt: `Redirect permanent / https://www.lab.example.org/` im `<VirtualHost *:80>`.
</Karte>

In der Liste stehen SSLProtocol, SSLCipherSuite, ServerTokens, ServerSignature und TraceEnable.
