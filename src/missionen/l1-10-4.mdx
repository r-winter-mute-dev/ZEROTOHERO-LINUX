Telnet ist weg. Ab jetzt meldet sich jeder per SSH an, am besten mit Schlüssel statt Passwort. **Deine Mission: Melde dich bei labor2 an, richte Schlüssel und den Agenten ein, erkenne einen geänderten Host-Schlüssel, baue einen Tunnel und härte den SSH-Server von werkstatt.** Lernziel 110.3.

## Die erste Verbindung

<Karte nr={1} titel="Wie SSH Vertrauen aufbaut">
SSH verschlüsselt die ganze Sitzung. Vorher müssen sich beide Seiten ausweisen:

1. **Der Server zeigt seinen Host-Schlüssel.** Jeder SSH-Server hat eigene Schlüsselpaare in `/etc/ssh/ssh_host_ed25519_key`, `/etc/ssh/ssh_host_ecdsa_key` und `/etc/ssh/ssh_host_rsa_key`, jeweils mit `.pub`. Ältere Server haben noch `ssh_host_dsa_key`. Sie entstehen bei der Installation. Beim ersten Kontakt kennt der Client den Schlüssel nicht und zeigt seinen **Fingerabdruck**: „The authenticity of host … can't be established“. Wer sicher gehen will, vergleicht den Fingerabdruck mit dem, den der Admin des Servers mit `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` abliest. Mit `yes` speichert der Client den Schlüssel in **~/.ssh/known_hosts**. Systemweit bekannte Schlüssel stehen in `/etc/ssh/ssh_known_hosts`. Debian speichert die Namen gehasht (`HashKnownHosts yes`), darum steht in known_hosts `|1|…` statt `labor2`.
2. **Der Benutzer weist sich aus**, mit Passwort oder mit Schlüssel.

`ssh lena@labor2` meldet lena an, `ssh labor2` nimmt den eigenen Benutzernamen. `ssh labor2 hostname` führt nur einen Befehl aus und kommt zurück. `-p 2222` wählt einen anderen Port.
</Karte>

## Schlüssel statt Passwort

<Karte nr={2} titel="Schlüsselpaare">
Ein Passwort kann man erraten, abfangen oder auf einer gefälschten Seite eingeben. Ein **Schlüsselpaar** nicht: Der private Schlüssel verlässt nie deinen Rechner, der Server bekommt nur den öffentlichen.

```
ssh-keygen -t ed25519 -C "lena@werkstatt"
```

legt `~/.ssh/id_ed25519` (privat) und `~/.ssh/id_ed25519.pub` (öffentlich) an. Die **Passphrase** schützt den privaten Schlüssel, falls jemand die Datei stiehlt. Typen: **ed25519** (kurz, schnell, empfohlen), **ecdsa**, **rsa** (dann mindestens 3072 Bit, `-b 4096`), **dsa** (veraltet, aktuelle OpenSSH-Versionen lehnen DSA ab). Die Dateien heißen entsprechend `id_rsa` und `id_rsa.pub`, `id_ecdsa` und `id_ecdsa.pub`, `id_dsa` und `id_dsa.pub`. Ohne `-t` erzeugt OpenSSH 9.2 auf Debian 12 einen RSA-Schlüssel.

`ssh-copy-id labor2` hängt deinen öffentlichen Schlüssel auf labor2 an **~/.ssh/authorized_keys** an, ein Schlüssel pro Zeile. Ab dann fragt ssh nur noch nach der Passphrase.

SSH ist streng mit Rechten. Der private Schlüssel braucht **600**, `~/.ssh` 700. Ist der Schlüssel für andere lesbar, ignoriert ssh ihn mit „UNPROTECTED PRIVATE KEY FILE“.
</Karte>

## Der Agent

<Karte nr={3} titel="ssh-agent und ssh-add">
Mit Passphrase musst du sie bei jeder Verbindung eingeben. Der **ssh-agent** hält entsperrte Schlüssel im Speicher. Er gibt ihnen eine Adresse über die Variablen `SSH_AUTH_SOCK` und `SSH_AGENT_PID`. Darum startet man ihn mit **`eval $(ssh-agent)`**: ssh-agent gibt Shell-Befehle aus, die diese Variablen setzen, und eval führt sie in der aktuellen Shell aus. Danach lädt **`ssh-add`** deine Schlüssel und fragt einmal nach der Passphrase. `ssh-add -l` zeigt geladene Schlüssel, `ssh-add -D` entfernt alle. Grafische Desktops starten meist schon einen Agenten beim Anmelden.

Auch GnuPG hat einen Agenten, `gpg-agent`. Er kann zusätzlich SSH-Schlüssel verwalten.
</Karte>

## Tunnel

<Karte nr={4} titel="Port-Weiterleitung und X11">
SSH kann andere Verbindungen durch die verschlüsselte Leitung tragen:

- **Lokaler Tunnel** `ssh -L 8080:localhost:80 labor2`: Was auf deinem Rechner an Port 8080 ankommt, geht durch SSH zu labor2 und dort an `localhost:80`. So erreichst du einen Dienst, der auf labor2 nur lokal lauscht oder hinter einer Firewall steht. Das Ziel wird **aus Sicht von labor2** angegeben.
- **Entfernter Tunnel** `ssh -R 9000:localhost:22 labor2`: umgekehrt. Port 9000 auf labor2 führt zu Port 22 bei dir.
- `-N` heißt: keinen Befehl ausführen, nur tunneln. `-f` schickt ssh nach der Anmeldung in den Hintergrund.
- **X11-Weiterleitung** `ssh -X labor2 xclock`: Das Programm läuft auf labor2, sein Fenster erscheint bei dir. SSH setzt dort `DISPLAY` auf `localhost:10.0`. `-Y` ist die „vertrauenswürdige“ Variante mit weniger Einschränkungen. Der Server muss `X11Forwarding yes` erlauben.
</Karte>

## Den Server härten

<Karte nr={5} titel="sshd_config">
Der SSH-Server liest **/etc/ssh/sshd_config** und, auf Debian 12, vorher alle Dateien `/etc/ssh/sshd_config.d/*.conf`. Für jede Option gilt der **erste** Wert, den sshd findet. Eigene Einstellungen gehören darum in eine Datei unter `sshd_config.d/`. Die wichtigsten Härtungen:

```
PermitRootLogin no            # root nie direkt, Debian-Vorgabe ist prohibit-password
PasswordAuthentication no     # nur noch Schlüssel
PubkeyAuthentication yes
X11Forwarding no              # wenn niemand X11 braucht
AllowUsers lena max           # nur diese Konten
```

Vor dem Neustart prüft **`sshd -t`** die Syntax. `sshd -T` zeigt die wirksamen Werte. Erst dann `systemctl restart ssh` (der Dienst heißt auf Debian ssh, auf RHEL sshd). Ein Tippfehler lässt den Dienst nicht mehr starten. Bestehende Sitzungen bleiben dabei offen, darum testet man eine neue Anmeldung, **bevor** man die alte schließt.
</Karte>
