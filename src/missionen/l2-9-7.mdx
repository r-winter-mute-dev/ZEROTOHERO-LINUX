Das Lager hat eine eigene Anwendung bekommen: lagerist-web läuft auf srv1 gleich zweimal, auf Port 8080 und 8081. Niemand soll diese Ports direkt kennen, alles soll über werkstatt unter lager.lab.example.org laufen. Lena möchte dafür Nginx vor alle Dienste stellen, auch vor Apache. **Deine Mission: Installiere Nginx neben Apache, stell ihn auf Port 80 vor Apache und leite lager.lab.example.org auf beide Instanzen von lagerist-web weiter.** Lernziel 208.4.

## Nginx

<Karte nr={1} titel="Aufbau">
**Nginx** arbeitet mit wenigen Prozessen und Ereignissen statt mit einem Prozess oder Thread pro Verbindung. Er ist schnell bei vielen gleichzeitigen Verbindungen und beliebt als **Reverse Proxy**: Er nimmt Anfragen von außen an und reicht sie an Server dahinter weiter. Ein Master-Prozess als root öffnet die Ports, Worker-Prozesse unter `www-data` arbeiten.

Die Konfiguration besteht aus **Direktiven** mit `;` am Ende und **Blöcken** in `{ }`, die ineinander stecken: `events`, `http`, darin `server` (wie ein virtueller Host), darin `location` (für Pfade). Kommentare beginnen mit `#`.

```
server {
    listen 80;
    server_name www.lab.example.org;
    root /var/www/www;
    index index.html;
    location / {
        try_files $uri $uri/ =404;
    }
}
```

Debian ordnet wie bei Apache: `nginx.conf` holt `conf.d/*.conf` und `sites-enabled/*`. Einschalten heißt verlinken (`ln -s /etc/nginx/sites-available/lager /etc/nginx/sites-enabled/`), ein a2ensite gibt es nicht. `nginx -t` prüft, `nginx -s reload` (oder `systemctl reload nginx`) lädt neu. Bei einem Fehler behält Nginx die alte Konfiguration.

Wählt Nginx einen `server`, zählen wie bei Apache erst Adresse und Port, dann `server_name`. Ohne Treffer antwortet der Block mit `default_server`, sonst der erste. Für Pfade gewinnt ein exakter Treffer (`location = /x`), dann ein passender regulärer Ausdruck (`location ~ \.php$`), sonst der längste Präfix.
</Karte>

## Vor anderen Servern

<Karte nr={2} titel="proxy_pass und upstream">
```
upstream lagerist {
    server 192.168.1.10:8080;
    server 192.168.1.10:8081;
}

server {
    listen 80;
    server_name lager.lab.example.org;
    location / {
        proxy_pass http://lagerist;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

**proxy_pass** schickt die Anfrage weiter, an eine Adresse (`http://127.0.0.1:8080`) oder an einen **upstream**-Block. Dessen Server bekommen die Anfragen reihum (mit `least_conn` an den mit den wenigsten Verbindungen, mit `ip_hash` immer an denselben pro Client). Antwortet einer nicht, nimmt Nginx den nächsten. Antwortet keiner, liefert er **502 Bad Gateway** und schreibt `connect() failed (111: Connection refused) while connecting to upstream` ins error.log.

Ohne Zusatz sieht das Backend als Host den Namen aus proxy_pass und als Client die Adresse von Nginx. **proxy_set_header** reicht darum den echten Namen (`$host`) und die echte Adresse des Clients (`X-Real-IP`, `X-Forwarded-For`) weiter. Apache als Backend wertet sie mit mod_remoteip aus.

Ein Schrägstrich am Ende von proxy_pass ändert den Pfad: `location /lager/ { proxy_pass http://lagerist/; }` macht aus `/lager/api` beim Backend `/api`. Ohne Schrägstrich bleibt `/lager/api` stehen.
</Karte>

<Merke>server ≈ VirtualHost, location ≈ Location. Jede Direktive mit Semikolon. proxy_pass zu upstream mit mehreren server-Zeilen, Host und X-Real-IP per proxy_set_header. nginx -t vor nginx -s reload. Zwei Server auf Port 80 geht nicht.</Merke>
