Willkommen in Prüfung 102. Dein erstes eigenes Messprogramm liegt schon in `~/bin`, aber die Shell findet es nicht. Und eine Einstellung, die du gerade gesetzt hast, kommt bei einem Skript nie an. **Deine Mission: Verstehe, welche Variablen eine Shell an ihre Kinder weitergibt und wie der Suchpfad funktioniert.** Lernziel 105.1.

## Wer erbt was?

<Karte nr={1} titel="Shell-Variablen und Umgebungsvariablen">
Jede Shell hat zwei Sorten von Variablen:

- **Shell-Variablen** gelten nur in dieser einen Shell. `PROJEKT=messung` legt so eine an. Um das Gleichheitszeichen darf kein Leerzeichen stehen.
- **Umgebungsvariablen** gibt die Shell an jedes Programm weiter, das sie startet, also auch an Skripte und neue Shells. `export PROJEKT` macht aus einer Shell-Variable eine Umgebungsvariable. `export PROJEKT=messung` macht beides in einem Schritt.

Die Weitergabe geht nur in eine Richtung: vom Elternprozess zum Kind, als **Kopie**. Ändert ein Kind eine Variable, merkt die Eltern-Shell davon nichts. Darum kann ein Skript nie die Variablen der Shell ändern, aus der du es startest. Das geht nur, wenn die Shell die Datei selbst liest, mit `source` (Mission 5.2).

Zum Anschauen:

| Befehl | zeigt |
|---|---|
| `echo $PROJEKT` | den Wert einer Variable |
| `env` oder `printenv` | alle Umgebungsvariablen |
| `printenv PATH` | eine Umgebungsvariable |
| `set` | alle Variablen der Shell (auch nicht exportierte) und alle Funktionen |

`unset PROJEKT` entfernt die Variable ganz. Jede neue Shell erhöht übrigens `SHLVL` um eins. Daran siehst du, wie tief du gerade steckst.
</Karte>

<Merke>VAR=wert gilt nur in dieser Shell. export VAR gibt sie an Kinder weiter, als Kopie. Kinder können die Eltern nie ändern. env zeigt die Umgebung, set alles.</Merke>

## Der Suchpfad

<Karte nr={2} titel="PATH und Variablen für einen einzigen Aufruf">
Tippst du einen Befehl ohne Schrägstrich, sucht die Shell ihn in den Verzeichnissen aus **PATH**, von links nach rechts. Der erste Treffer gewinnt. Das aktuelle Verzeichnis steht absichtlich nicht drin. Darum startest du ein Skript im aktuellen Verzeichnis mit `./skript`.

Eigene Programme legst du nach `~/bin` und hängst das Verzeichnis an den Pfad an:

```
PATH="$HOME/bin:$PATH"
```

Vorne angehängt gewinnt dein Programm gegen gleichnamige Systemprogramme, hinten angehängt (`PATH="$PATH:$HOME/bin"`) verliert es. Die Anführungszeichen schützen vor Leerzeichen. Das gilt bis zum Ende der Sitzung. Dauerhaft wird es erst in einer Startdatei (Mission 5.2). Debian macht das in `~/.profile` übrigens schon selbst, sobald `~/bin` beim Login existiert.

Eine Variable nur für **einen** Befehl setzt du direkt davor: `EINHEIT=mV messen`. Die Shell legt sie in die Umgebung dieses einen Programms und lässt deine eigene Shell unverändert. `env` kann noch mehr: `env -i befehl` startet mit leerer Umgebung, `env -u VAR befehl` ohne eine bestimmte Variable.
</Karte>

<Merke>PATH wird von links durchsucht, . steht nicht drin. PATH="$HOME/bin:$PATH" hängt vorne an. VAR=wert befehl gilt nur für diesen Aufruf.</Merke>
