Die Zone lab.example.org läuft auf werkstatt. Jetzt kommen drei Wünsche auf einmal: Die Logs sollen statt nackter Adressen Namen zeigen, die Werkhalle will ihre Maschinen unter werkhalle.lab.example.org selbst verwalten, und wenn werkstatt ausfällt, soll die Zone trotzdem erreichbar bleiben. **Deine Mission: Richte die Rückwärtszone ein, delegiere die Unterzone an srv1 und mach srv1 zum zweiten Nameserver für lab.example.org.** Lernziel 207.2.

## Rückwärts und von der Wurzel aus

<Karte nr={1} titel="Rückwärtszonen und Wurzelserver">
Für die Frage „welcher Name gehört zu 192.168.1.40?“ gibt es den Baum **in-addr.arpa**. Die Adresse steht dort rückwärts, damit wie bei Namen das Allgemeine rechts steht: Das Netz 192.168.1.0/24 ist die Zone `1.168.192.in-addr.arpa`, der Rechner .40 darin der Name `40`. Für IPv6 gibt es **ip6.arpa**, jede Hex-Ziffer (Nibble) einzeln und rückwärts.

```
zone "1.168.192.in-addr.arpa" {
    type primary;
    file "/etc/bind/db.192.168.1";
};

; db.192.168.1
$TTL 3600
@   IN SOA ns1.lab.example.org. hostmaster.lab.example.org. ( 2026112701 7200 3600 1209600 900 )
@   IN NS  ns1.lab.example.org.
40  IN PTR laser.lab.example.org.
```

Im PTR steht der volle Name mit Punkt, sonst hinge named `1.168.192.in-addr.arpa.` an. Gefragt wird mit `dig -x 192.168.1.40` oder `host 192.168.1.40`.

Ein rekursiver Server beginnt bei der **Wurzel**. Woher er deren Adressen kennt, steht in einer Zone vom Typ **hint**: auf Debian `zone "." { type hint; file "/usr/share/dns/root.hints"; };`, auf Red Hat die Datei `/var/named/named.ca`. named fragt beim Start einen der Server aus der Liste nach der aktuellen Liste (priming). Die Datei muss man darum selten anfassen. Eine frische Liste liefert `dig @a.root-servers.net . NS`.
</Karte>

## Delegieren und verteilen

<Karte nr={2} titel="Eine Unterzone abgeben">
Wer werkhalle.lab.example.org selbst verwaltet, betreibt dafür eine eigene Zone auf eigenem Server, hier srv1. Die übergeordnete Zone lab.example.org **delegiert** sie mit NS-Einträgen:

```
werkhalle     IN NS  ns.werkhalle.lab.example.org.
ns.werkhalle  IN A   192.168.1.10
```

Der A-Eintrag heißt **Glue**: Der Nameserver liegt selbst in der delegierten Zone, also könnte niemand seine Adresse erfragen, ohne sie schon zu kennen. Darum steht sie zusätzlich in der übergeordneten Zone. Liegt der Nameserver außerhalb, ist kein Glue nötig.

Fragt man werkstatt ohne Rekursion (`dig +norec`), antwortet er nicht mit der Adresse, sondern mit einem **Verweis** (referral): leere Antwort, kein aa, in AUTHORITY die NS-Einträge, in ADDITIONAL der Glue. Mit Rekursion folgt er dem Verweis selbst.
</Karte>

<Karte nr={3} titel="Ein zweiter Server">
Ein **sekundärer** Server holt die ganze Zone per **Zonentransfer** (AXFR, über TCP) vom primären. Auf srv1 sieht der Eintrag so aus:

```
zone "lab.example.org" {
    type secondary;
    primaries { 192.168.1.23; };
    file "/var/cache/bind/db.lab.example.org";
};
```

Ältere Schreibweise: `type slave; masters { … };`. named schreibt die Kopie selbst, die Datei liegt darum in seinem Arbeitsverzeichnis. Seit BIND 9.9 speichert er sie im Format **raw** statt als Text.

Auf dem primären Server gehört srv1 als `@ IN NS ns2…` mit Adresse in die Zone. Dann schickt named bei jeder neuen Seriennummer ein **NOTIFY** an alle Nameserver der Zone, und die holen sich die Änderung sofort, statt bis zum nächsten Refresh zu warten. Server, die nicht als NS eingetragen sind, benachrichtigt man mit `also-notify { … };`.

Ohne Einschränkung darf in BIND 9.18 jeder die ganze Zone abholen, also alle Rechnernamen. `allow-transfer { 192.168.1.10; };` im Zonenblock (oder in den Optionen für alle) erlaubt es nur noch dem sekundären Server.
</Karte>

<Merke>Rückwärtszone: Netz rückwärts plus in-addr.arpa, PTR mit vollem Namen. Delegation: NS in der übergeordneten Zone, Glue nur, wenn der Server in der Unterzone liegt. Sekundär: NS eintragen, Serial hoch, NOTIFY, allow-transfer begrenzen.</Merke>
