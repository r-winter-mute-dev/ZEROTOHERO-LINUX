Heute Nacht läuft ein neues Auswerteprogramm zum ersten Mal über die Messreihen. Niemand weiß, ob es sauber arbeitet, und eine Vollsicherung würde Stunden dauern. Außerdem soll die älteste Platte /dev/sdc raus. **Deine Mission: Friere die Messreihen vor dem Lauf per Snapshot ein, roll nach einem Unfall zurück, räum die alte Platte im laufenden Betrieb leer und übe das Aktivieren einer Volume Group.** Lernziel 204.3.

## Snapshots

<Karte nr={1} titel="Einfrieren mit Copy-on-Write">
Ein LVM-Snapshot ist ein zweites LV, das den Zustand des Originals zum Zeitpunkt des Anlegens zeigt. Er kopiert dabei nichts: Erst wenn im Original ein Block **überschrieben** wird, rettet LVM vorher den alten Inhalt in den Snapshot (Copy-on-Write, COW).

```
sudo lvcreate -s -L 5G -n vor-update daten/messungen
```

Die Größe bei `-L` ist deshalb nicht die Größe des Originals, sondern der Platz für **Änderungen**. Wie voll er ist, zeigt `lvs` in der Spalte Data%. Läuft er auf 100 %, wird der Snapshot **ungültig** (Attr mit I) und ist verloren. Darum gibt es in /etc/lvm/lvm.conf:

```
activation {
	snapshot_autoextend_threshold = 70     # ab 70 % belegt …
	snapshot_autoextend_percent = 20       # … um 20 % vergrößern (100 schaltet das aus)
}
```

Einen Snapshot kannst du wie jedes LV einhängen, am besten nur lesend: `mount -o ro /dev/daten/vor-update /mnt/vor-update`. Das ist auch der klassische Weg zu einer konsistenten Sicherung: Snapshot anlegen, davon sichern, Snapshot löschen. Snapshots bremsen Schreibzugriffe auf das Original, sie sind für Stunden oder Tage gedacht, nicht für Monate.

Neben diesen klassischen Snapshots gibt es Thin Provisioning (`lvcreate --thin`), bei dem Snapshots aus einem gemeinsamen Pool wachsen. Das Lernziel verlangt nur die klassische Variante.
</Karte>

## Zurückrollen

<Karte nr={2} titel="lvconvert --merge">
Ist das Original kaputt, schreibt `lvconvert --merge` den Stand des Snapshots zurück ins Original. Der Snapshot verschwindet danach.

```
sudo lvconvert --merge daten/vor-update
  Delaying merge since origin is open.
  Merging of snapshot daten/vor-update will occur on next activation of daten/messungen.
```

Ist das Original eingehängt, verschiebt LVM das Zusammenführen auf die **nächste Aktivierung**. Bei der Wurzel ist das der nächste Neustart, bei einem Datenvolume reicht:

```
sudo umount /srv/messungen
sudo lvchange -an daten/messungen
sudo lvchange -ay daten/messungen      # jetzt läuft der Merge
sudo mount /srv/messungen
```

Den Snapshot selbst darfst du dabei nicht eingehängt haben.
</Karte>

## Aktivieren und Platten räumen

<Karte nr={3} titel="vgchange und pvmove">
Ein LV hat erst dann Gerätedateien, wenn es **aktiv** ist. Beim Start aktiviert udev bzw. ein Dienst alle gefundenen VGs. Von Hand:

```
sudo vgchange -ay            # alle VGs aktivieren
sudo vgchange -an daten      # alle LVs von daten deaktivieren (vorher aushängen)
sudo lvchange -ay daten/archiv
```

Das braucht man, wenn eine Platte mit einer VG an einen anderen Rechner wandert (vorher `vgchange -an` und `vgexport`, dort `vgimport` und `vgchange -ay`), im Rettungssystem oder nach `vgscan`, wenn LVM neue Geräte suchen soll. `lvscan` zeigt ACTIVE oder inactive je LV.

Eine alte Platte aus der VG zu nehmen geht ohne Ausfallzeit:

```
sudo pvmove /dev/sdc1               # Extents auf die anderen PVs verschieben
sudo vgreduce daten /dev/sdc1       # leeres PV aus der VG nehmen
sudo pvremove /dev/sdc1             # LVM-Label löschen
```

pvmove arbeitet im Hintergrund mit einem temporären Spiegel und kann nach einem Abbruch mit `pvmove` ohne Argument fortgesetzt werden. Es braucht genug freie Extents auf den übrigen PVs.
</Karte>
