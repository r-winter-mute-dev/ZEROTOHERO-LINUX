Zwei Notfälle an einem Morgen. Auf werkstatt kennt niemand mehr das root-Passwort, die Kollegin, die es gesetzt hat, ist im Urlaub. Und ein Prüfrechner bleibt nach einem missglückten Update mit `grub>` stehen. **Deine Mission: Nutze das GRUB-Menü und die GRUB-Befehlszeile, setze das root-Passwort über init=/bin/bash neu und starte einen Kernel von Hand, wenn die grub.cfg fehlt.** Lernziel 202.2.

## Ins Menü eingreifen

<Karte nr={1} titel="Kernelparameter für einen einzigen Start">
Im GRUB-Menü öffnet **e** den markierten Eintrag. Du siehst die Befehle, die GRUB für diesen Eintrag ausführt, darunter die Zeile `linux /boot/vmlinuz-… root=UUID=… ro quiet`. Alles hinter dem Pfad des Kernels sind **Kernelparameter**. Du kannst sie hier ändern und mit **Strg+X** (oder F10) starten. Die Änderung gilt nur für diesen einen Start.

| Parameter | Ergebnis |
|---|---|
| `systemd.unit=rescue.target` (kurz `single`, `1` oder `s`) | **Rescue-Modus**: lokale Dateisysteme eingehängt, wenige Grunddienste, root-Passwort nötig |
| `systemd.unit=emergency.target` (kurz `emergency`) | **Emergency-Modus**: nur `/`, nur lesbar, kein Dienst, root-Passwort nötig |
| `init=/bin/bash` | der Kernel startet eine Shell als Prozess 1, ganz ohne systemd und ohne Passwort |
| `rw` statt `ro` | die Wurzel wird gleich beschreibbar eingehängt |

Unter SysV-init entsprach dem Rescue-Modus der Runlevel 1 (oder S), den man auch mit `telinit 1` erreichte.

Rescue und Emergency verlangen das root-Passwort. Ist es verloren oder das Konto gesperrt, hilft nur **init=/bin/bash**. Dann hängt der Kernel `/` so ein, wie es die Parameter sagen, meist nur lesbar. Also: `mount -o remount,rw /`, dann `passwd`, dann `exec /sbin/init`, damit der normale Start weiterläuft. Wer physischen Zugang zur Tastatur hat, hat damit root. Deshalb schützt man GRUB auf Rechnern in offenen Räumen mit einem Passwort (`set superusers` und `password_pbkdf2` in `/etc/grub.d/40_custom`).
</Karte>

## Die GRUB-Befehlszeile

<Karte nr={2} titel="Starten ohne grub.cfg">
Findet GRUB seine `grub.cfg` nicht, bleibt es mit `grub>` stehen. Aus dem Menü kommst du mit **c** an dieselbe Befehlszeile. Sie versteht unter anderem:

| Befehl | Zweck |
|---|---|
| `ls` | alle Platten und Partitionen, etwa `(hd0) (hd0,gpt1) (hd0,gpt2)` |
| `ls (hd0,gpt2)/boot` | Dateien auf einer Partition |
| `set root=(hd0,gpt2)` | Partition, auf die sich folgende Pfade beziehen |
| `linux /boot/vmlinuz-… root=/dev/nvme0n1p2 ro` | Kernel mit Parametern laden |
| `initrd /boot/initrd.img-…` | initramfs laden |
| `boot` | starten |
| `configfile (hd0,gpt2)/boot/grub/grub.cfg` | ein Menü von anderswo laden |
| `insmod`, `search --fs-uuid`, `cat`, `echo` | Module laden, Partition per UUID suchen, Dateien lesen |

Nach dem Start ist der Rechner nur einmal gerettet. Dauerhaft hilft erst eine neue `grub.cfg`: `update-grub` (Debian) oder `grub2-mkconfig -o /boot/grub2/grub.cfg` (Red Hat). Kernelparameter für jeden Start gehören nach `/etc/default/grub` in `GRUB_CMDLINE_LINUX` (immer) oder `GRUB_CMDLINE_LINUX_DEFAULT` (nicht bei den Einträgen für den Wiederherstellungsmodus).
</Karte>

Im Entwurf 5.0 (201.4) bleiben Rettungs- und Notfallmodus Thema.
