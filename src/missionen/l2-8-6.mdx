srv1 holt die Zone lab.example.org jetzt per Zonentransfer ab, freigegeben nur für seine Adresse. Lena ist das zu wenig: Adressen lassen sich fälschen. Außerdem sollen die Laborrechner die Namen der Firma (wiki.firma.intern) auflösen können, und die Firma verlangt, dass lab.example.org signiert wird. **Deine Mission: Sichere den Zonentransfer mit einem gemeinsamen Schlüssel, leite firma.intern an srv1 weiter und signiere die Zone mit DNSSEC.** Lernziel 207.3.

## Transfers mit Schlüssel

<Karte nr={1} titel="TSIG">
**TSIG** (transaction signature, RFC 8945) sichert einzelne Nachrichten zwischen zwei Servern: Beide kennen denselben geheimen Schlüssel und hängen an jede Nachricht einen HMAC an. Wer den Schlüssel nicht hat, bekommt keinen Transfer, egal von welcher Adresse er kommt. TSIG schützt so Zonentransfers, NOTIFY, dynamische Updates und auch rndc (dessen Schlüssel ist ein TSIG-Schlüssel).

```
$ tsig-keygen -a hmac-sha256 ns1-ns2 > ns1-ns2.key
$ cat ns1-ns2.key
key "ns1-ns2" {
    algorithm hmac-sha256;
    secret "Wq0mK4bX…";
};
```

Die Datei kommt auf beide Server, gehört root und ist nur für named lesbar (`640 root:bind`), und named.conf bindet sie mit `include` ein. Auf dem primären Server erlaubt man den Transfer dann nur noch mit Schlüssel: `allow-transfer { key ns1-ns2; };`. Auf dem sekundären sagt ein **server**-Block, dass er beim primären immer signiert fragt: `server 192.168.1.23 { keys { ns1-ns2; }; };`.

Von Hand prüft man mit `dig -k ns1-ns2.key @ns1 lab.example.org AXFR` oder `dig -y hmac-sha256:ns1-ns2:GEHEIM …`. Ältere Anleitungen erzeugen TSIG-Schlüssel mit `dnssec-keygen -a HMAC-MD5`. Das geht seit BIND 9.13 nicht mehr, und MD5 gilt ohnehin als zu schwach.
</Karte>

## Split DNS

<Karte nr={2} titel="Interne Namen weiterleiten">
Die Namen unter firma.intern gibt es nur im Firmennetz, auf srv1. Das Internet kennt sie nicht. Damit werkstatt sie trotzdem auflöst, schickt er alle Fragen dazu gezielt an srv1, während alles andere den normalen Weg nimmt:

```
zone "firma.intern" {
    type forward;
    forward only;
    forwarders { 192.168.1.10; };
};
```

So entsteht **Split DNS**: Je nach Server oder Netz bekommt man unterschiedliche Antworten, intern mehr als extern. Ein zweiter Weg sind **views** in named.conf. Ein Server liefert dann mit `match-clients { 192.168.1.0/24; };` dem eigenen Netz eine andere Fassung einer Zone als dem Rest.

Eine Falle mit DNSSEC: Die signierte Wurzel beweist, dass es die Top-Level-Domain intern nicht gibt. Ein prüfender Resolver hält die Antwort von srv1 darum für gefälscht und meldet SERVFAIL, im Journal „insecurity proof failed“. Für private Namen schaltet `validate-except { "firma.intern"; };` in den Optionen die Prüfung gezielt ab. Sauberer ist ein Name unter einer echten, eigenen Domain oder unter home.arpa.
</Karte>

## DNSSEC

<Karte nr={3} titel="Signierte Zonen">
**DNSSEC** sichert die Daten selbst: Jede Gruppe gleicher Einträge bekommt eine Signatur, die jeder prüfen kann. Die neuen Eintragstypen:

| Typ | Inhalt |
|---|---|
| DNSKEY | öffentliche Schlüssel der Zone, Flag 256 = ZSK, 257 = KSK |
| RRSIG | Signatur über eine Gruppe von Einträgen |
| DS | Fingerabdruck des KSK, steht in der **übergeordneten** Zone |
| NSEC, NSEC3 | beweisen, dass es einen Namen nicht gibt |

Zwei Schlüssel sind üblich: Der **ZSK** (zone signing key) signiert die Einträge, der **KSK** (key signing key) nur die DNSKEY-Einträge. Den ZSK kann man so wechseln, ohne die übergeordnete Zone zu bemühen. Die Kette des Vertrauens läuft von der Wurzel über den DS jeder Ebene bis zum Schlüssel der Zone.

Von Hand signiert:

```
cd /etc/bind
sudo dnssec-keygen -a ECDSAP256SHA256 lab.example.org        # ZSK
sudo dnssec-keygen -a ECDSAP256SHA256 -f KSK lab.example.org # KSK
sudo dnssec-signzone -S -o lab.example.org db.lab.example.org
```

dnssec-keygen legt je Schlüssel zwei Dateien an: `Klab.example.org.+013+41200.key` (öffentlich, 013 ist die Nummer des Algorithmus) und `….private`. dnssec-signzone mit `-S` sucht die Schlüssel selbst und schreibt `db.lab.example.org.signed` und `dsset-lab.example.org.` mit dem DS für die übergeordnete Zone. In named.conf zeigt `file` danach auf die `.signed`-Datei. Signaturen laufen nach 30 Tagen ab, also muss man regelmäßig neu signieren, sonst wird die Zone ungültig.

Weil das mühsam ist, signiert named das heute selbst: `dnssec-policy default;` im Zonenblock (KASP, key and signing policy) erzeugt Schlüssel, signiert und erneuert. Der Entwurf 5.0 der Lernziele setzt darauf und streicht dnssec-keygen und dnssec-signzone. In 4.5 stehen sie noch.

Auf Clientseite zeigt `dig +dnssec` die Signaturen, das Flag **ad** heißt, dass der Resolver die Kette geprüft hat. **DANE** (RFC 6698) baut darauf auf: Ein **TLSA**-Eintrag wie `_25._tcp.mail.lab.example.org. IN TLSA 3 1 1 …` nennt den Fingerabdruck des TLS-Zertifikats eines Dienstes. Ohne DNSSEC wäre er wertlos.
</Karte>
