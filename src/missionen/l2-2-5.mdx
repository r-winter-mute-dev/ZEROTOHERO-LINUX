Der Treiber der Messbox läuft. Jetzt kommen die Wünsche: Das Messteam will die Box unter einem eigenen Namen laden, das WLAN von messpc soll Strom sparen, und seit dem Herbst taucht im Kernelprotokoll eine Warnung zur Netzwerkkarte auf. **Deine Mission: Verwalte Module im laufenden Betrieb, setze Parameter dauerhaft und finde Fehler in der Modulkonfiguration.** Lernziel 201.3.

## Module ansehen, laden und entladen

<Karte nr={1} titel="lsmod, modinfo, modprobe und /sys/module">
`lsmod` zeigt die geladenen Module, es formatiert nur `/proc/modules`. Die Spalte **Used by** nennt, wie oft ein Modul benutzt wird, und dahinter die Module, die es brauchen. Steht dort mehr als 0, lässt es sich nicht entladen: `rmmod snd` meldet dann „Module snd is in use by: snd_hda_intel …“. Erst müssen die Benutzer weg, oder das Gerät darf nicht mehr in Gebrauch sein.

`modprobe -r MODUL` entlädt ein Modul und alle Abhängigkeiten, die danach niemand mehr braucht. `rmmod` entlädt nur genau eines.

**modinfo MODUL** zeigt die Datei, die Beschreibung, die Abhängigkeiten (`depends`) und alle Parameter (`parm`). `modinfo -p MODUL` zeigt nur die Parameter. Den aktuellen Wert eines Parameters liest du unter **/sys/module/MODUL/parameters/**, sofern der Treiber ihn dort sichtbar macht. Manche Werte lassen sich dort sogar zur Laufzeit ändern.

Parameter gibst du beim Laden mit: `modprobe iwlwifi power_save=1`. Dauerhaft gehören sie in eine Datei unter **/etc/modprobe.d/**, die auf `.conf` endet:

```
options iwlwifi power_save=1
```

Die neue Einstellung wirkt erst beim nächsten Laden. Ist das Modul schon geladen, also `modprobe -r iwlwifi && modprobe iwlwifi`. Für Module, die schon im initramfs geladen werden, musst du zusätzlich das initramfs neu bauen. Auf der Kernelzeile geht dasselbe als `iwlwifi.power_save=1`.
</Karte>

<Merke>lsmod: Used by 0 = entladbar. modinfo -p: Parameter. /sys/module/MODUL/parameters: aktuelle Werte. Dauerhaft: options MODUL param=wert in /etc/modprobe.d/*.conf, dann neu laden.</Merke>

## Namen, Sperren und der Start

<Karte nr={2} titel="alias, blacklist, install und modules-load.d">
Die Konfiguration von modprobe steht in `/etc/modprobe.d/*.conf` (dazu `/run/modprobe.d` und `/lib/modprobe.d`). Die wichtigsten Befehle:

| Zeile | Wirkung |
|---|---|
| `alias messbox labsensor` | `modprobe messbox` lädt labsensor |
| `options MODUL param=wert` | Parameter bei jedem Laden |
| `blacklist pcspkr` | pcspkr wird nicht mehr **automatisch** über seine Aliase geladen. Von Hand mit `modprobe pcspkr` geht es weiter. |
| `install pcspkr /bin/false` | statt zu laden, läuft /bin/false. Damit scheitert auch `modprobe pcspkr`. |
| `softdep MODUL pre: ANDERES` | lädt ANDERES vorher |

Modulnamen dürfen Minus oder Unterstrich enthalten, beide gelten als gleich. Die Datei von `usb_storage` heißt `usb-storage.ko`, und `modprobe usb-storage` funktioniert genauso.

Wie kommt ein Treiber zum Gerät? Jedes Modul nennt in seinen Aliasen die Geräte, die es bedient, zum Beispiel `usb:v1209p0001…` für die Messbox. depmod sammelt sie in `modules.alias`. Steckt jemand das Gerät an, meldet der Kernel dessen Kennung, und udev lädt das passende Modul. Darum musst du Hardware-Treiber fast nie von Hand laden. Für Module ohne eigenes Gerät, etwa Dateisysteme oder Netzwerkfunktionen, gibt es **/etc/modules-load.d/*.conf** mit einem Modulnamen pro Zeile. Debian liest zusätzlich `/etc/modules`.

Hilfreich zur Fehlersuche: `modprobe -c` zeigt die gesamte wirksame Konfiguration, `modprobe -n -v MODUL` zeigt, was passieren würde, ohne es zu tun, `modprobe --show-depends MODUL` die Abhängigkeiten. Unbekannte Parameter lehnt der Kernel nicht ab, sondern lädt das Modul und meldet in dmesg `unknown parameter '…' ignored`.
</Karte>

<Merke>alias: anderer Name. blacklist: nicht automatisch. install MODUL /bin/false: gar nicht. Beim Start: /etc/modules-load.d. Hardware lädt udev über modules.alias. Unbekannte Parameter: dmesg „unknown parameter … ignored“.</Merke>
