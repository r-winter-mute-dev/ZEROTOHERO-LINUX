Die Messreihen wachsen jedes Jahr um ein paar hundert Gigabyte, und niemand weiß genau, wie viel nächstes Jahr dazukommt. Feste Partitionen sind dafür die falsche Wahl: Wer zu klein schneidet, muss später umziehen. **Deine Mission: Bau aus zwei Platten einen LVM-Speicherpool, schneide daraus ein Volume für die Messreihen und häng es dauerhaft ein.** Lernziel 204.3.

## Drei Schichten

<Karte nr={1} titel="PV, VG, LV">
Der **Logical Volume Manager** schiebt eine Schicht zwischen Platten und Dateisysteme:

- **Physical Volume (PV):** eine Platte, Partition oder ein RAID wie /dev/md0, mit einem LVM-Label versehen. Partitionen dafür bekommen den Typ **8e** (MBR) bzw. „Linux LVM“ (GPT, gdisk 8E00).
- **Volume Group (VG):** ein Pool aus einem oder mehreren PVs. LVM teilt ihn in gleich große **Extents** (Physical Extents, PE), Standard 4 MiB, beim Anlegen mit `vgcreate -s` änderbar.
- **Logical Volume (LV):** eine Folge von Extents aus der VG, die sich wie eine Partition verhält. Die Extents dürfen über mehrere PVs verteilt sein.

Der Gewinn: Ein LV lässt sich im Betrieb vergrößern, verkleinern, umbenennen, auf andere Platten verschieben und per Snapshot einfrieren. Eine VG kann jederzeit um weitere PVs wachsen.

Technisch steckt der **Device Mapper** des Kernels dahinter. Jedes aktive LV ist ein Gerät /dev/dm-N. Dazu legt udev zwei Namen an: /dev/VG/LV und /dev/mapper/VG-LV. Enthält ein Name einen Bindestrich, wird er unter /dev/mapper verdoppelt: das LV vor-update in daten heißt dort daten-vor--update.
</Karte>

## Anlegen

<Karte nr={2} titel="pvcreate, vgcreate, lvcreate">
```
sudo pvcreate /dev/sdc1 /dev/sdd1
sudo vgcreate daten /dev/sdc1 /dev/sdd1
sudo lvcreate -L 200G -n messungen daten      # feste Größe
sudo lvcreate -l 50%FREE -n archiv daten      # Anteil am freien Platz, auch %VG
sudo lvcreate -l 1000 -n klein daten          # in Extents
```

`-L` nimmt Größen mit Einheit (k, m, g, t), `-l` Extents oder Prozent. Danach ist das LV ein leeres Blockgerät: `mkfs.ext4 /dev/daten/messungen`, einhängen, in die fstab.

Was es gibt, zeigen drei Befehlspaare: **pvs, vgs, lvs** für eine Zeile je Objekt, **pvdisplay, vgdisplay, lvdisplay** ausführlich (PE Size, Total PE, Free PE, LV Status), **pvscan, vgscan, lvscan** suchen auf allen Geräten. Alle sind in Wahrheit das Programm `lvm`: `lvm vgs` tut dasselbe.

In die fstab schreibst du /dev/daten/messungen oder /dev/mapper/daten-messungen. Beide Namen sind stabil, anders als /dev/dm-0, dessen Nummer sich ändern kann.

Weg geht es in umgekehrter Reihenfolge: `lvremove`, `vgremove`, `pvremove`.
</Karte>

## lvm.conf

<Karte nr={3} titel="Wo LVM sucht und was es sich merkt">
Die zentrale Datei ist **/etc/lvm/lvm.conf**. Für die Prüfung wichtig sind zwei Abschnitte:

```
devices {
	filter = [ "a|^/dev/sd.*|", "a|^/dev/md.*|", "r|.*|" ]
}
activation {
	snapshot_autoextend_threshold = 70
	snapshot_autoextend_percent = 20
}
```

Der **filter** ist eine Liste regulärer Ausdrücke, `a` nimmt Geräte an, `r` weist sie ab, der erste Treffer gilt. So verhindert man etwa, dass LVM die Mitglieder eines RAID oder die Platten einer virtuellen Maschine für eigene PVs hält. `lvmconfig` zeigt die wirksame Konfiguration.

Bei jeder Änderung sichert LVM die Metadaten der VG als Text nach **/etc/lvm/backup/VG**, ältere Stände nach /etc/lvm/archive/. Mit `vgcfgrestore` lässt sich daraus eine versehentlich gelöschte Struktur wiederherstellen.
</Karte>
