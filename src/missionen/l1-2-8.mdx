Dein Labor besteht aus virtuellen Maschinen, und die meisten Server heute auch. Wer zehn gleiche Server braucht, installiert nicht zehnmal, sondern klont eine **Vorlage**. Dabei lauern Fallen: Zehn Server mit demselben SSH-Schlüssel und derselben Maschinen-ID sind ein Problem. **Deine Mission: Mach aus einer VM eine saubere Vorlage.** Lernziel 102.6.

## Virtuelle Maschinen und Container

<Karte nr={1} titel="Zwei Arten, Systeme zu teilen">
- Eine **virtuelle Maschine** bekommt vom **Hypervisor** (zum Beispiel KVM, VirtualBox, VMware, Xen) simulierte Hardware: Prozessor, Speicher, Platte, Netzwerkkarte. Darauf läuft ein vollständiges Betriebssystem mit **eigenem Kernel**. Du kannst also Windows auf Linux betreiben.
- Ein **Container** hat keinen eigenen Kernel. Er **teilt sich den Kernel des Hosts** und ist nur ein abgeschotteter Bereich mit eigenen Prozessen, Dateien und Netz. Das ist leichter und schneller, aber es laufen nur Linux-Programme auf einem Linux-Host.
  - Ein **System-Container** (etwa LXC) enthält ein ganzes System mit Init-System und Diensten, fast wie eine VM.
  - Ein **Anwendungs-Container** (etwa Docker oder Podman) enthält nur eine einzige Anwendung und was sie braucht.
</Karte>

<Merke>VM = eigener Kernel. Container = Kernel des Hosts. System-Container = ganzes System, Anwendungs-Container = eine Anwendung.</Merke>

<Karte nr={2} titel="In der Cloud">
Bei einer **IaaS-Cloud** (Infrastructure as a Service) mietest du solche Bausteine:

- **Recheninstanzen** (compute instances): virtuelle Maschinen in verschiedenen Größen.
- **Blockspeicher** (block storage): virtuelle Platten, die man an Instanzen hängt und wieder abhängt.
- **Netzwerk**: virtuelle Netze, öffentliche IP-Adressen und Firewallregeln.

Instanzen startet man aus **Images**: fertigen Abbildern eines Systems. Dasselbe Prinzip gibt es bei Containern (Container-Images) und bei VMs im eigenen Rechenzentrum (Vorlagen, templates).
</Karte>

<Karte nr={3} titel="Gasttreiber">
Ein System in einer VM läuft schneller und bequemer mit Treibern, die wissen, dass sie virtuell sind. **virtio** sind solche Treiber für Platte und Netz unter KVM. Für VirtualBox gibt es die **Guest Additions**, für VMware **open-vm-tools**, für KVM den **qemu-guest-agent**. Sie liefern zum Beispiel gemeinsame Zwischenablage und Ordner, eine bessere Bildschirmauflösung, Zeitabgleich und ein sauberes Herunterfahren auf Befehl des Hypervisors. `systemd-detect-virt` verrät, ob und unter welcher Virtualisierung ein System läuft.
</Karte>

## Eine Vorlage bauen

<Karte nr={4} titel="Was jeder Klon für sich braucht">
Klonst du eine VM, entstehen exakte Kopien. Diese Dinge müssen danach aber **einmalig** sein:

- **Hostname** in `/etc/hostname`, sonst heißen alle Server gleich.
- **SSH-Host-Schlüssel** in `/etc/ssh/ssh_host_*`. Mit ihnen weist sich der Server gegenüber Clients aus. Haben alle Klone denselben Schlüssel, kann einer sich als der andere ausgeben.
- **machine-id** in `/etc/machine-id` (D-Bus liest sie über `/var/lib/dbus/machine-id`). Viele Dienste unterscheiden Rechner daran. Manche DHCP-Clients (etwa systemd-networkd) leiten ihre Kennung daraus ab, gleiche IDs können dann zu gleichen IP-Adressen führen.
- **MAC-Adressen** und Netzwerkeinstellungen. Die MAC vergibt meist der Hypervisor neu.

Deshalb **verallgemeinert** man die Vorlage, bevor man sie klont: Host-Schlüssel löschen, machine-id leeren. Ist `/etc/machine-id` beim Start leer, erzeugt systemd eine neue. Die SSH-Schlüssel erzeugt `ssh-keygen -A` neu, auf Debian auch `dpkg-reconfigure openssh-server`.
</Karte>

<Merke>Vor dem Klonen: SSH-Host-Schlüssel löschen, machine-id leeren. Nach dem Klonen: Hostname setzen, Schlüssel neu erzeugen.</Merke>

<Hinweis art="sicherheit" titel="Leer, nicht gelöscht">
Bei /etc/machine-id gilt: leeren, nicht löschen. Eine leere Datei erzeugt systemd beim nächsten Start neu. Fehlt die Datei ganz, kann es je nach System beim Start Probleme geben.
</Hinweis>

## cloud-init

<Karte nr={5} titel="Einrichten beim ersten Start">
In der Cloud geht das noch weiter: Images enthalten meist **cloud-init**. Beim ersten Start holt es sich vom Cloud-Anbieter die **user-data** und richtet die Instanz danach ein, zum Beispiel so:

```
#cloud-config
hostname: web01
users:
  - name: lena
    ssh_authorized_keys:
      - ssh-ed25519 AAAA… lena@laptop
packages:
  - nginx
```

Hostname, Benutzer, Schlüssel und Pakete stehen dann nicht im Image, sondern kommen beim Start dazu. Für LPIC-1 reicht es, cloud-init und seinen Zweck zu kennen.
</Karte>
