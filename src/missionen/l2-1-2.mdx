Diesmal ist es nicht die CPU. srv1 reagiert träge, Anmelden per SSH dauert Sekunden, aber top zeigt kaum Rechenlast. **Deine Mission: Lies den Speicher richtig, erkenne, wann Swap zum Problem wird, und finde den Dienst, der immer mehr Speicher verbraucht.** Lernziel 200.1.

## Freier Speicher ist verschwendeter Speicher

<Karte nr={1} titel="free richtig lesen">
```
               total        used        free      shared  buff/cache   available
Mem:           7,8Gi       1,8Gi       818Mi        51Mi       5,2Gi       4,3Gi
Swap:          2,0Gi          0B       2,0Gi
```

Nur 818 MiB **free**? Kein Grund zur Sorge. Linux nutzt Speicher, den gerade niemand braucht, als **Cache** für Dateien (buff/cache). Will ein Programm mehr Speicher, gibt der Kernel den Cache sofort wieder her. Die wichtige Spalte ist **available**: So viel können Programme noch bekommen, ohne dass etwas ausgelagert werden muss.

Wird es eng, lagert der Kernel selten genutzte Seiten in den **Swap** aus. Ein bisschen belegter Swap ist harmlos, wenn die Seiten dort einfach liegen bleiben. Schlimm wird es, wenn ständig aus- und wieder eingelagert wird. Dann wartet jeder Prozess auf die Platte, der Rechner wird zäh, und der Kernel-Thread **kswapd** taucht in top auf. Ist auch der Swap voll, beendet der **OOM-Killer** (out of memory) einen Prozess, meist den größten. Das steht dann im Kernel-Protokoll (`journalctl -k`).
</Karte>

<Merke>free wenig ist normal, available zählt. Swap belegt ist harmlos, ständiges Ein- und Auslagern (si, so) nicht. Ist alles voll, beendet der OOM-Killer einen Prozess.</Merke>

## vmstat

<Karte nr={2} titel="Ein Werkzeug für alles auf einmal">
**vmstat** zeigt in einer Zeile Prozesse, Speicher, Swap, Platten-I/O, Interrupts und CPU. `vmstat 1 5` gibt fünf Zeilen im Abstand von einer Sekunde aus.

```
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 0  1 504924 376300   4100  27000  742  985   805  1141  231  380  7  3 85  5  0
```

| Spalte | Bedeutung |
|---|---|
| r | Prozesse, die laufen oder auf einen Kern warten |
| b | Prozesse, die **blockiert** auf Ein- oder Ausgabe warten (Zustand D) |
| swpd | belegter Swap in KiB |
| free, buff, cache | Speicher in KiB |
| si, so | **swap in, swap out**: KiB pro Sekunde aus dem Swap geholt bzw. hineingeschrieben |
| bi, bo | **blocks in, blocks out**: Blöcke pro Sekunde von der Platte gelesen bzw. auf sie geschrieben |
| in, cs | Interrupts und Kontextwechsel pro Sekunde |
| us sy id wa st | wie in top |

**Achtung:** Die **erste Zeile** zeigt Mittelwerte seit dem Start des Rechners. Für den aktuellen Zustand liest du ab der zweiten Zeile. Ohne Intervall gibt vmstat nur diese eine, wenig hilfreiche Zeile aus.

`vmstat -s` zeigt Zähler als Liste, `vmstat -d` Statistiken pro Platte, `vmstat -S M` Werte in MiB.
</Karte>

<Merke>vmstat 1 5, erste Zeile ignorieren. r läuft, b blockiert. si/so: Swap pro Sekunde, dauerhaft über null ist schlecht. bi/bo: Blöcke von und zur Platte.</Merke>

<Hinweis titel="Neustart ist keine Lösung">
Der Neustart von messd kauft dir Zeit. Das Leck bleibt, und in drei Tagen ist der Speicher wieder voll. In Mission 1.5 rechnest du aus, wann genau. Bis das Update kommt, könntest du dem Dienst eine Obergrenze setzen, etwa mit `MemoryMax=` in der Unit-Datei. Dann trifft der OOM-Killer messd und nicht die Datenbank.
</Hinweis>
